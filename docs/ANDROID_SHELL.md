# Androidアプリ（殻）の仕様

DayFlow の画面はWeb（このリポジトリの直下）で、Androidアプリ（`android/`）はそれを表示する殻。
殻の仕事は2つだけ：**予定の時刻に通知を出すこと**と、**通知のボタンが押された時刻を画面に渡すこと**。
記録そのもの（IndexedDB）は画面側が持つ。殻は記録に触らない。

## 構成

| ファイル（`android/app/src/main/java/app/dayflow/shell/`） | 役割 |
| --- | --- |
| `MainActivity` | WebView で `BuildConfig.APP_URL` を開く。ファイル選択、通知の許可、システムバーの余白 |
| `Bridge` | 画面から呼ばれる入口（`window.DayFlowNative`） |
| `Store` | 端末に覚えておくもの（予定表、計測中、ためた操作、予約中のID） |
| `Scheduler` | アラームの予約と取り消し |
| `Notifier` | 通知の組み立て |
| `AlarmReceiver` | 予約時刻に通知を出す |
| `ActionReceiver` | 通知のボタンを受ける（画面は開かない） |
| `BootReceiver` | 再起動・アプリ更新のあとに予約を張り直す |

外部ライブラリは使っていない（Android標準のAPIだけ）。対象は Android 10（API 29）以上。

## 画面 → 殻（`window.DayFlowNative`）

### `replaceSchedule(json)`

開始の通知の予定表。呼ばれるたびに全部置き換える。中身が前回と同じなら何もしない。

```json
[{ "id": "u-g08a", "date": "2026-11-17", "name": "行政法規 第8回 前半", "start": 1200, "minutes": 130, "when": 1794913200000 }]
```

- `when`：通知を出す時刻（エポックミリ秒）。ふつうは予定の開始時刻。「10分後」が押された予定は遅れている。
- `start`：予定の開始（0時からの分。表示用）。`minutes`：予定の長さ（終了確認の時刻に使う）。
- 画面は、まだ始めていない予定のうち `when` が「15分前より後」のものを渡す。
- 殻の扱い：`when` が未来なら、その時刻に通知。過ぎて10分以内なら、`when`＋10分の出し直しだけ予約。それ以上過ぎていたら通知しない。
- 通知：タイトル＝`HH:MM 名前`、ボタン＝［開始］`start`／［10分後］`snooze10`／［スキップ］`skip`。
- 反応がなければ10分後に1回だけ出し直す。

### `setRunning(json)`

計測中の実績。空文字なら「計測していない」。

```json
{ "sessionId": "s…", "planId": "u-g08a", "name": "行政法規 第8回 前半", "startedAt": 1794913620000, "endAt": 1794921420000 }
```

- `endAt` に終了確認の通知を出す。タイトル＝`名前 終わった？`、ボタン＝［完了］`finish`／［＋15分］`extend15`。
- 空文字が来たら、終了確認の予約と通知を取り消す。

### `takePendingActions()`

通知のボタンが押された記録を返し、**返したら空にする**。

```json
[{ "action": "start", "id": "u-g08a", "at": 1794913620000 }, { "action": "finish", "id": "", "at": 1794920400000 }]
```

- `at`：ボタンが押された時刻。画面はこれを実績の開始・終了時刻に使う。
- 画面は、起動時・前面に戻ったとき・殻から合図があったときに呼び、`at` の順に反映する。

### `saveFile(name, text)`

バックアップを「ダウンロード/DayFlow」に保存する。成功したら保存先の名前、失敗したら空文字を返す。

### `status()`

`{"version": "2.0.12", "notifications": true, "exactAlarms": true}`。設定画面に出す。

## 殻 → 画面

ボタンが押されたら、殻は**必ずためる**（`takePendingActions` 用）。そのうえで画面が生きていれば
`window.dayFlowDrain()` を呼んで、すぐ取りに来させる。記録の経路をこの1本にして、二重に記録されないようにしている。

`window.dayFlowNotificationAction(action, id, at)` は v1.2 の殻のために残してある（この殻は使わない）。

| `action` | `id` | 画面側の動き |
| --- | --- | --- |
| `start` | 予定のID | その予定の実績を `at` から開始。別の計測が進行中なら無視 |
| `snooze10` | 予定のID | 予定は動かさず、通知時刻だけ `at`＋10分にする |
| `skip` | 予定のID | 予定をスキップにする |
| `finish` | 空 | 計測中の実績を `at` で終了 |
| `extend15` | 空 | 予定終了を `at`＋15分に延ばす |

## ボタンが押されたときの殻の動き

1. 通知を消し、押された時刻とアクションをためる。画面（Activity）は開かない。
2. 続きの通知を自分で予約する（画面が閉じていても動くように）。
   - `start`：出し直しを取り消し、いま＋`minutes` に終了確認を予約。
   - `snooze10`：10分後に開始の通知をもう一度。
   - `skip`：出し直しを取り消す。
   - `finish`：終了確認の予約を取り消す。
   - `extend15`：15分後に終了確認をもう一度。
3. 画面が生きていれば `dayFlowDrain()` を呼ぶ。

終了確認に反応がないまま30分以上たった場合は、次にアプリを開いたときに画面が「いつ終わった？」と尋ねる（殻は何もしない）。

## 受け入れ条件（実機で確認する）

1. 20:00 の予定で、20:00（±1分）にWatchが振動し、通知に［開始］［10分後］［スキップ］が出る。
2. スマホの画面を消したままWatchで［開始］→ 予定の長さが過ぎると「終わった？」が届く →［完了］。そのあとアプリを開くと、押した時刻どおりの実績が1件できている。
3. ［10分後］を押すと10分後にもう一度通知が来て、アプリ上の予定の時刻は変わっていない。
4. アプリを開いた状態でWatchのボタンを押すと、画面がその場で変わり、実績は1件だけ。
5. スマホを再起動しても、次の予定の通知が来る。
6. 画面（Web）を更新してpushすると、アプリを入れ直さずに新しい画面になる。
7. 設定画面の「書き出す」で、ダウンロード/DayFlow にファイルができる。「読み込む」でファイルを選べる。

## うまくいかないときに見る場所

- 通知が来ない：設定画面の「Androidアプリとの連携」の行（通知の許可、時刻どおりの通知）。スマホ側でDayFlowの通知がオンか、電池の最適化で止められていないか。
- 通知は来るがWatchに出ない：スマホの Galaxy Wearable アプリで、Watchに通知を出すアプリに DayFlow が入っているか。
- 画面が開かない：`BuildConfig.APP_URL`（`android/app/build.gradle` の `appUrl`）が、ログインなしで開けるURLか。
